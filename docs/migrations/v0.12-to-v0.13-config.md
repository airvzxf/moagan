# Migration guide — v0.12 → v0.13 config schema

> **Target audience**: operators who maintain a `config.toml` (or
> `~/.config/moagan/config.toml`) and want to migrate from the v0.12
> legacy `[providers.<name>]` single-table shape to the v0.13
> `[[providers.<name>]]` array-of-tables shape.
>
> **Why now**: v0.13.0 introduces a new TOML schema for the
> `[providers]` block. The legacy shape continues to load with a
> `tracing::warn!` per section — you do **not** have to migrate
> immediately. But the legacy shape will be **removed in v0.15**, so
> an operator who upgrades through v0.14.x without migrating will hit
> a hard parse error at the v0.15 bump. This guide is the canonical
> reference for the migration window.
>
> **Background**: see
> [`docs/adr/0003-config-schema-array-of-tables.md`](../adr/0003-config-schema-array-of-tables.md)
> for the *why* (the design rationale, the alternatives considered,
> and the consequences). This guide is the *how*.

---

## 1. Will my config still work?

**Yes.** A v0.12 TOML loads on a v0.13 binary with the same runtime
behaviour. The dual-mode deserializer
([`src/config/dual_mode.rs`](../../src/config/dual_mode.rs)) accepts
both shapes and emits a single `tracing::warn!` per legacy section
so you can see at a glance which sections still need migration:

```
WARN config: `[providers.minimax]` (single-table form) is deprecated \
     in v0.13; use `[[providers.minimax]]` (array-of-tables) with \
     `models = ["<id>", ...]` instead. The conversion preserves the \
     legacy shape in-memory; support for the single-table form will \
     be removed in v0.15.
```

What you need to know about the warning:

- It fires **once per section**, not once per model. A TOML with
  three legacy sections emits three warnings; a mixed TOML (one
  legacy, one new) emits one warning for the legacy section only.
- The warning is **per-section deprecation**, not per-model
  deprecation. If your TOML has `[providers.minimax]` with five
  models, you see one warning, not five.
- The warning is **per-call to `Config::load()`**, which means the
  CLI's `--config` flag, the `MOAGAN_CONFIG` env var, and the XDG
  fallback all produce the same warning shape. It is not persisted
  to disk; it lives in the JSONL telemetry stream under the
  `config::legacy` target.

The runtime behaviour is bit-identical (modulo the new
`MOAGAN_<SECTION>_MAX_TOKENS` env var — see §4 below). You can defer
the migration to any point in the v0.13.x or v0.14.x window.

## 2. How do I migrate?

A section-by-section rewrite. The canonical conversion rules:

| v0.12 (legacy) | v0.13 (new) |
|---|---|
| `[providers.<name>]` (single table) | `[[providers.<name>]]` (array-of-tables) |
| `models = [{ id = "x", ... }, { id = "y", ... }]` | `models = ["x", "y"]` (flat strings) |
| Per-model `endpoint = "…"` | The `[[…]]` entry carries the endpoint instead |
| Per-model `max_tokens = N` | Removed; use `MOAGAN_<SECTION>_MAX_TOKENS=N` env var (see §4) |
| Section-level `endpoint = "…"` | Required `endpoint = "…"` on every entry |

The concrete transformation: each legacy section with a single
section-level endpoint becomes one `[[…]]` entry carrying all model
ids. A legacy section with per-model endpoint overrides becomes
multiple `[[…]]` entries, one per unique effective endpoint (the
bridge groups models by their resolved endpoint — see ADR-0003 D-3).

### Worked example — `minimax`

```toml
# v0.12.x — LEGACY
[providers.minimax]
endpoint = "https://api.minimax.io/anthropic/v1/messages"
models = [
  { id = "MiniMax-M3",            max_tokens = 1000000 },
  { id = "MiniMax-M2.7",          max_tokens = 1000000 },
  { id = "MiniMax-M2.7-highspeed", max_tokens = 1000000 },
  { id = "MiniMax-M2.5",          max_tokens = 1000000 },
]
temperature = 0.6
top_p = 0.95
```

```toml
# v0.13.x — NEW
[[providers.minimax]]
endpoint = "https://api.minimax.io/anthropic/v1/messages"
models = [
  "MiniMax-M3",
  "MiniMax-M2.7",
  "MiniMax-M2.7-highspeed",
  "MiniMax-M2.5",
]
temperature = 0.6
top_p = 0.95
```

The 2-3 legacy entries collapse into 1 entry because every model
shared the section-level endpoint. The four `max_tokens = 1_000_000`
lines disappear because the per-model knob is gone — the new
default is `1_000_000` via the `resolve_max_tokens` chain's
fallback rung (see §4).

### Worked example — `opencode` (multi-endpoint)

```toml
# v0.12.x — LEGACY: 19 models, 3 wire formats, per-model `endpoint`
[providers.opencode]
models = [
  { id = "kimi-k3",     endpoint = "https://opencode.ai/zen/go/v1/chat/completions" },
  { id = "glm-5.1",     endpoint = "https://opencode.ai/zen/go/v1/chat/completions" },
  { id = "glm-5.3-flash", endpoint = "https://opencode.ai/zen/go/v1/chat/completions" },
  { id = "deepseek-v4-flash", endpoint = "https://opencode.ai/zen/go/v1/chat/completions" },
  { id = "minimax-m3",  endpoint = "https://opencode.ai/zen/go/v1/messages" },
  { id = "minimax-m2.7", endpoint = "https://opencode.ai/zen/go/v1/messages" },
  { id = "qwen3.7-max", endpoint = "https://opencode.ai/zen/go/v1/messages" },
  { id = "gpt-5.6-luna", endpoint = "https://opencode.ai/zen/go/v1/responses" },
  { id = "muse-spark-1.2-contributor", endpoint = "https://opencode.ai/zen/go/v1/responses" },
]
temperature = 1.0
top_p = 0.95
```

```toml
# v0.13.x — NEW: 3 entries, one per wire format
[[providers.opencode]]
endpoint = "https://opencode.ai/zen/go/v1/chat/completions"
models = ["kimi-k3", "glm-5.1", "glm-5.3-flash", "deepseek-v4-flash"]
temperature = 1.0   # only the first entry needs the section-level knobs
top_p = 0.95

[[providers.opencode]]
endpoint = "https://opencode.ai/zen/go/v1/messages"
models = ["minimax-m3", "minimax-m2.7", "qwen3.7-max"]

[[providers.opencode]]
endpoint = "https://opencode.ai/zen/go/v1/responses"
models = ["gpt-5.6-luna", "muse-spark-1.2-contributor"]
omit_max_tokens = true   # gpt-5.6-luna rejects the *presence* of `max_tokens`
```

The 9 entries become 3, the wire-format suffix lives on the entry
URL, and the per-entry knobs (`temperature`, `omit_max_tokens`, …)
are picked up by `SectionKnobs::merge_first_wins` (see ADR-0003 D-2)
when the bridge collapses them into the runtime `ProviderConfig`.

## 3. What about `MOAGAN_MINIMAX_MODEL` and `MOAGAN_MINIMAX_ENDPOINT`?

Both still work in v0.13.

### `MOAGAN_MINIMAX_ENDPOINT=<url>`

Rewrites the **per-model `endpoint`** on the first `minimax` model
whose endpoint contains `/messages` (the canonical MiniMax URL
pattern). The bridge leaves the per-entry `endpoint` populated on
each `ModelConfig`, so the env var rewrite targets the per-model
field directly — no section-level lookup.

Behavioural change vs. v0.12: in v0.12 the env var rewrote
`ProviderConfig::endpoint` (section-level), so a single env var
overrode every model in the section. In v0.13 it rewrites the
first model's per-entry endpoint, so the override is scoped to the
specific model the dispatcher routes to MiniMax. The opencode
section's `minimax-m3/m2.7/m2.5` aliases (which sit on
`/v1/messages` but are routed through opencode's pool) are
**not** touched — the env var only targets the canonical
`minimax` section, matching the v0.10 split documented in
plan §6.5.

If you need to redirect the opencode aliases, edit
`config.toml` directly — there is no per-alias env var.

### `MOAGAN_MINIMAX_MODEL=<id>`

Rewrites the first model's id on the canonical `minimax` section
(same scope as `MOAGAN_MINIMAX_ENDPOINT`). The runtime behaviour is
unchanged from v0.12.

`MOAGAN_MINIMAX_MODEL` is **deprecated** in v0.13 — the same
behaviour is now available as the per-model `MOAGAN_MINIMAX_MAX_TOKENS`
(see §4 below) or by editing the TOML. The env var will be removed
in **v0.15** alongside the legacy TOML syntax.

## 4. What about `MOAGAN_<SECTION>_MAX_TOKENS`?

**New in v0.13.** This is the operator-facing per-`(section, model)`
`max_tokens` knob that was previously embedded in the legacy TOML
(per-model `max_tokens = N`). The full chain, in priority order:

```
  ┌─────────────────────────────────────────────────────────────┐
  │ 1. Env var   MOAGAN_<SECTION>_MAX_TOKENS (highest priority) │
  │    e.g. MOAGAN_MINIMAX_MAX_TOKENS=131072                    │
  ├─────────────────────────────────────────────────────────────┤
  │ 2. Cache     <MOAGAN_HOME>/max_tokens_auto.toml             │
  │    populated by the auto-probe at startup                   │
  │    filtered by >= MIN_AUTOPROBE_FLOOR (1024)                │
  ├─────────────────────────────────────────────────────────────┤
  │ 3. Operator  the per-model knob from the legacy TOML        │
  │    (still honoured via the side-channel until v0.15)        │
  ├─────────────────────────────────────────────────────────────┤
  │ 4. Kind cap  MINIMAX_MAX_TOKENS_CAP, DEEPSEEK_MAX_TOKENS_CAP│
  │    hardcoded per-provider safety net                        │
  ├─────────────────────────────────────────────────────────────┤
  │ 5. Default   DEFAULT_MAX_TOKENS = 1_000_000 (lowest)        │
  └─────────────────────────────────────────────────────────────┘
```

Implementation:
[`src/llm/max_tokens.rs`](../../src/llm/max_tokens.rs) — see the
`resolve_max_tokens` function. The five-rung chain is documented
in ADR-0003 D-4.

### Concrete operator recipes

Pin a specific `(section, model)` ceiling without editing the
TOML:

```bash
export MOAGAN_MINIMAX_MAX_TOKENS=131072     # MiniMax-M3, etc.
export MOAGAN_OPENCODE_MAX_TOKENS=32768     # every opencode model
export MOAGAN_DEEPSEEK_MAX_TOKENS=8192      # DeepSeek Chat / Reasoner
```

Section-name normalisation: the helper uppercases the section name
and folds `.` / `-` to `_`, so `opencode-go` resolves to
`MOAGAN_OPENCODE_GO_MAX_TOKENS` and `mini-max` (hypothetical) to
`MOAGAN_MINI_MAX_MAX_TOKENS`.

Out-of-range values (e.g. `MOAGAN_MINIMAX_MAX_TOKENS=10`, below
`MIN_AUTOPROBE_FLOOR`) emit a `tracing::warn!` and fall through to
the next rung. Unparseable values (e.g. `=abc`) emit a warning and
fall through. Empty / whitespace values are silently ignored.

## 5. When is legacy removed?

**v0.15.** The deprecation window is two minor versions per the
operator's "deprecate-then-remove" convention documented in
`AGENTS.md` ("Deprecated fields are kept for one minor cycle, then
removed"). The v0.13.0 release notes spell out the window:

```
config: `[providers.<name>]` (single-table form) is deprecated in
v0.13; use `[[providers.<name>]]` (array-of-tables) with
`models = ["<id>", ...]` instead. The conversion preserves the
legacy shape in-memory; support for the single-table form will be
removed in v0.15.
```

A CI guard script
(`scripts/check-no-legacy-config-schema.sh`, planned for a v0.13.x
follow-up) will flag drift in `docs/` and `tests/fixtures/` so a
v0.15.0 contributor cannot accidentally re-introduce legacy shapes
into the documentation surface.

If you need more than one minor cycle, open an issue and reference
this ADR — the operator's policy allows case-by-case extensions for
operators with audited legacy configs that cannot be migrated
before v0.15.0 ships.

## 6. FAQ

### 6.1 — Will my `mock` section still use `mock://local`?

**Yes.** The mock provider is the one section whose
`ProviderConfig::endpoint` is consulted by the `is_mock` check in
`src/llm/provider.rs:1351-1356`. The bridge propagates the first
mock entry's endpoint to `ProviderConfig::endpoint` (the only
section where it does so) so the runtime check keeps working
unchanged. The `mock-model` model id is registered in
`Config::default()` and your TOML only needs to override the
`mock_dir` if you want canned responses from a non-default path.

### 6.2 — Does the opencode pool still group 19 models?

**Yes — 19 models on 3 entries.** The pool name (`spec.endpoint`
or `spec.models.first().id` fallback) is computed once at
construction; the bridge populates both fields correctly. A
section with three `[[providers.opencode]]` entries produces one
pool with 19 `ModelConfig` records, each carrying its entry's
endpoint on `ModelConfig::endpoint`. Round-robin and breaker logic
keep working unchanged. See
[`src/llm/openai_compatible.rs:141-192`](../../src/llm/openai_compatible.rs)
for the pool wiring.

### 6.3 — Is `MOAGAN_HOME` / `api_keys.toml` untouched?

**Yes.** The API-key plumbing
([`src/llm/api_keys.rs`](../../src/llm/api_keys.rs)) reads
`~/.config/moagan/api_keys.toml` and the `MOAGAN_<SECTION>_API_KEY`
env vars (e.g. `OPENCODE_API_KEY`, `DEEPSEEK_API_KEY`,
`MINIMAX_API_KEY`). The v0.13 redesign does **not** touch the
`api_keys.toml` schema; it stays a flat `[providers]` table keyed by
section name. If you put a key into `moagan.toml` instead of
`api_keys.toml`, the loader emits a warning via
`Config::warn_unknown_provider_keys` (added in PR #1+2, runs on every
load).

### 6.4 — Does the legacy `[[providers.X.models]]` form still work?

**Yes, with a deprecation warning.** The v0.12 "section-array" form
— `[providers.X]` plus `[[providers.X.models]]` entries with
inline-table `id` — is classified as legacy by the deserializer
(the inline-table shape of `models[].id` is the discriminator, not
the section header). The warning fires once per section and the
bridge handles the conversion. Migrating to the new
`[[providers.X]]` form is the canonical fix.

### 6.5 — Can I mix legacy and new sections?

**Yes, per-section.** A TOML with `[providers.minimax]` (legacy) and
`[[providers.deepseek]]` (new) loads cleanly. The legacy section
emits one warning; the new section does not. The two views are
collapsed into the canonical `providers_legacy: BTreeMap<String,
ProviderConfig>` by `Config::compute_legacy_providers()` after
`Config::load()`.

### 6.6 — Will my `MOAGAN_MAX_TOKEN_AUTO=false` env var still disable the probe?

**Yes.** The probe opt-out env var (`MOAGAN_MAX_TOKEN_AUTO`) and the
per-section `max_token_auto_enabled = false` knob are independent of
the schema redesign. The probe runs against the auto-populated
`(section, model)` pairs in `cfg.providers_legacy`; whether the
schema is legacy or new does not change the probe's behaviour.
`MOAGAN_TEMPERATURE_AUTO` (added in v0.12.15) is also untouched.

### 6.7 — Where do I see the new schema in action?

[`config.example.toml`](../../config.example.toml) is rewritten in
the v0.13 shape. The four commented-out provider sections
(`minimax`, `deepseek`, `opencode`, `mock`) and the LEGACY block at
the bottom (commented out) show the side-by-side conversion. The
`tests/fixtures/config/v013_dual_mode/` directory carries four TOML
fixtures exercising legacy-only, new-only, mixed, and
legacy-with-per-model-max_tokens shapes; the integration tests in
`tests/integration_config_dual_mode.rs` validate the round-trip.

## 7. Troubleshooting

### 7.1 — I see a `WARN config: `[providers.minimax]` is deprecated` warning

Expected: the section is still in the v0.12 legacy single-table form.
Migrate it to `[[providers.minimax]]` with `models = ["…"]` to
silence the warning. The runtime behaviour is unchanged; the warning
fires once per `Config::load()` call (i.e. once per CLI invocation,
once per `audit verify` invocation, once per test binary that
loads the config).

If the warning is showing up in **every** CLI invocation and you've
already migrated the TOML, double-check that you're not loading a
stale config from a different path. The loader precedence is:

1. `$MOAGAN_CONFIG` (highest — explicit override)
2. `./moagan.toml` or `./.moagan.toml` (cwd-local)
3. `${XDG_CONFIG_HOME:-~/.config}/moagan/config.toml` (XDG fallback)
4. Built-in defaults

A `./moagan.toml` that you forgot about will shadow the XDG file.

### 7.2 — I set `MOAGAN_MINIMAX_MAX_TOKENS=131072` but the wire body uses 1_000_000

Either the env var is not reaching the process (check
`printenv | grep MOAGAN`), or the helper falls through because the
value is out of range. The helper accepts values in
`[MIN_AUTOPROBE_FLOOR, MAX_AUTOPROBE_CEILING]` = `[1024, 2^30]`;
`131_072` is in range, so the most likely cause is an empty /
unparseable value. Run with `--log-format json` and grep for
`"MOAGAN_MINIMAX_MAX_TOKENS"` in the structured log — an
unparseable or out-of-range value emits a `tracing::warn!` with the
exact value and the floor/ceiling bounds. If you see no warning,
the value was accepted and the runtime used it; double-check the
model id (the helper looks up `(section, model)` exactly).

### 7.3 — The auto-probe cache (`<MOAGAN_HOME>/max_tokens_auto.toml`) is corrupted

The helper filters cache entries by `>= MIN_AUTOPROBE_FLOOR` (1024)
so a corrupt entry with `max_tokens = 0` or `max_tokens = 100` is
silently ignored. To force a re-probe, delete the sidecar file:

```bash
rm ~/.local/share/moagan/max_tokens_auto.toml    # or $MOAGAN_HOME/max_tokens_auto.toml
```

The next run regenerates the cache from the live upstreams. If
`<MOAGAN_HOME>` is on a read-only filesystem, the probe fails
with `Err(IoError::Write)` — this is a pre-existing limitation, not
introduced by v0.13.

### 7.4 — My `.env` file has `OPENCODE_API_KEY=…` and the dispatcher doesn't find it

The `.env` loader (file at `$MOAGAN_HOME/.env` or the cwd) reads
into `process::Command`'s child env. Verify the key is in the
section that matches the dispatcher lookup — `OPENCODE_API_KEY` for
the `opencode` section, `MINIMAX_API_KEY` for `minimax`, etc. The
section name is canonical; legacy `OPENCODE_GO_API_KEY` from v0.9
is **gone** (closed out in v0.12.18, commit `aa09a6e`). If your
`.env` still has `OPENCODE_GO_API_KEY`, rename it to
`OPENCODE_API_KEY` and reload.

### 7.5 — `MOAGAN_HOME` points to a read-only filesystem

Pre-existing limitation, not introduced by v0.13. The auto-probe
fails to write the sidecar with `Err(IoError::Write)`; the runtime
falls back to the operator_cap / kind_hard_cap / default chain as
documented in §4. To work around, set `MOAGAN_MAX_TOKEN_AUTO_SAVE=false`
(the probe still runs but does not persist), or set
`MOAGAN_HOME` to a writable path. The plan §6.4 documents the
follow-up for a fully atomic sidecar (deferred to v0.14).
