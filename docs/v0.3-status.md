### Capacidad

- **Trigger ladder (V4 §5.3)**: `should_decompose(brief) == true`
  cuando hay ≥3 constraints, ≥3 deliverables, o magic words
  (`subproblem`, `phase`, `depends on`, `after`, `once`).
  La 5ª condición de V4 §5.3 («mix arquitectura + dominio +
  implementación») queda como follow-up del catálogo aditivo:
  requeriría añadir un campo `domain_tags: Vec<String>` a
  `Brief` y bumpear `schema_version`. Hoy los otros 3 triggers
  cubren el mismo espacio problemático desde otro ángulo.
- **Trivial path**: cuando la ladder falla, la fase escribe
  `ProblemGraph::trivial(...)` a `problem_graph.json` SIN
  gastar una llamada LLM. Tarda 0 tokens y 0 ms.
- **DAG generation**: cuando la ladder pasa, la fase llama al
  rol `decomposer` (T=0.3, top_p=0.9, max_tokens=4096) y
  parsea la respuesta como `ProblemGraph`.
- **DAG repair**: la fase valida el grafo con Kahn; un grafo
  con ciclos o dependencias colgantes se repara eliminando
  nodos ofensivos. Si todo se cae, vuelve al trivial path.
- **Sketch DAG distribution**: `SketchPhase` consume
  `problem_graph.json` cuando existe y es no-trivial. Las
  sketches se distribuyen por nodo (1 sketch por nodo o
  `ceil(count / node_count)` por nodo).
- **SQLite mirror**: la tabla `problem_graphs` (migración v006)
  registra `(run_id, brief_blake3, should_decompose, node_count,
  at_unix)` por run. Permite queries estilo `moagan inspect`
  del tipo «qué runs hicieron decompose y cuántos nodos?».
- **Wiring**: `DecomposePhase` se inserta entre `RoutePhase` y
  `SketchPhase` SOLO en `Mode::Deep`. El resto de modos no
  insertan la fase y pagan 0 overhead.

### Métricas

- **LLM calls adicionales**: 1 por deep run (la llamada al
  `decomposer`). Se omite cuando la ladder corta.
- **Test coverage**: 9 unit tests + 8 integration tests + 17
  smoke tests = 34 nuevos. Todos pasan.
- **Compat**: la migración v006 es aditiva. DBs pre-v006
  toleran el nuevo código vía `record_problem_graph` que
  detecta `user_version < 6` y retorna `Ok(())`.

### Limitaciones documentadas

1. `HARD_INCOMPATIBILITIES` (D.13.15) NO implementado — sigue
   como opt-in del catálogo aditivo. La síntesis intra-cluster
   (Phase D) no bloquea pares incompatibles.
2. ~~`Proposal.source_nodes` se rellena con la lista de nodos
   que la propuesta cubre, pero el campo todavía no se
   computa automáticamente en `ProposePhase`. El wiring del
   populate queda para una sub-fase futura.~~ **Resuelto en
   sub-fase H commit 3** (`feat(propose): populate

3. `SketchPhase` consume el DAG pero no paraleliza por capa

   las sketches en paralelo (cap por `max_parallelism`). El

4. `pedgraph` NO se añade como dep. La implementación de Kahn

### Capacidad

- **`Ranking.stability_score`** — `Option<HashMap<proposal_id, f32>>`
  con la fracción `[0.0, 1.0]` de perturbaciones bajo las que el
  proposal mantuvo su posición. `None` cuando el check se omitió
  (config deshabilitado, n=0, o una sola propuesta).
- **`Ranking.stability_label`** — `Option<StabilityLabel>` con
  `Stable | Sensitive` (enum serializado en lowercase por la
  convención del spec).
- **`Ranking.stability_sigma`** — `Option<f32>` con el sigma
  efectivo de la perturbación, registrado para correlación con
  la sensibilidad detectada.
- **`Config::stability`** — bloque nuevo con `enabled`,
  `n_perturbations`, `sigma_default`, `sigma_interactive`,
  `sensitive_threshold`, `seed`. Defaults conservadores que no
  perturban ganadores claros (sigma 0.05).
- **`src/ranking/stability.rs`** — funciones puras
  `perturb_weights`, `stability_score`, `stability_check`. Box-
  Muller vía `fastrand` (ya en deps); clip `[0.0, 2.0]`. Sin
  nuevas dependencias.
- **`RankPhase` paso 5.6** — corre el check post-reemplazo
  (Phase F), persiste en `rankings/ranking.json`, emite
  `tracing::info!` con el verdict.
- **V4 §5.14 trigger** — sobre `Sensitive` + `ctx.interactive`,
  abre `CheckpointKind::Custom` con la pregunta embebiendo
  `top_score`, `threshold`, `sigma`, `winner`. Default yes
  (continuar). Runs no interactivos caen en
  `<skipped:non_interactive>` (audit trail).
- **`Proposal.source_nodes` populate** — `ProposePhase::compute_source_nodes`
  lee `problem_graph.json` cuando es no-trivial y asigna a
  cada proposal los ids de los nodos cuyo Jaccard con el texto
  del proposal es `<= 0.7` (mismo umbral que
  `RankPhase::CLUSTER_THRESHOLD`). Asignación ordenada por
  `(distancia, id)` para idempotencia.

### Métricas

- **LLM calls adicionales**: 0. El check es pura cómputo
  sobre las `Aggregated` sidecars existentes.
- **Test coverage**: 10 unit tests en `stability.rs` + 3 unit
  tests en `propose.rs` + 8 integration tests en
  `tests/integration_phase_h.rs` + 25 smoke checks =
  **46 nuevos**. Todos pasan.
- **Compat**: los 3 campos nuevos en `Ranking` son
  `#[serde(default, skip_serializing_if = "Option::is_none")]`,
  así que los sidecars v0.2 (sin los campos) siguen parseando
  como `None` en cada uno. Tests
  `legacy_ranking_without_stability_fields_parses` +
  `ranking_with_stability_round_trips_json` pinan el contrato.
- **Crate version**: `Cargo.toml` bumped a `0.3.0` (cierra la
  discrepancia #2 que arrastraba v0.2-status desde `main`).
  El bump a `0.4.0` queda para cuando v0.3 (H + I + J + K) esté
  cerrada.

### Limitaciones documentadas

1. `proptest` no se añade como dep — los invariantes de la
   perturbación (clip, monotonicidad de sigma, fracciones suman
   1.0) están cubiertos por tests unitarios con seeds fijos.
   Si el repo más adelante adopta `proptest`, las versiones
   `proptest!` ya están escritas en `stability.rs` (sección
   `proptests`).
2. El mirror a SQLite del verdict de estabilidad se hace vía
   `tracing::info!` por ahora; un nuevo campo en la tabla `runs`
   puede aterrizar en sub-fase posterior (Phase I, dashboard).
3. `Resolution::Modify(text)` del checkpoint es informativo; el
   pipeline no re-rankea con la nota del usuario todavía —
   `moagan rerank` sigue siendo la vía explícita para
   re-correr el rank phase.
