## 1. TL;DR

PR #421 (`feat(llm): reasoning gating via models.dev catalog`,
`7f693a2`) was opened on 2026-08-12 with the goal of wiring the
`reasoning` flag from the models.dev catalog into the request builder
so upstreams that reject `reasoning_tokens` (e.g. the `kimi-*` family)
stop seeing the field on the wire. The PR's headline deliverable is a
new module `src/llm/reasoning_gate.rs` (~620 LoC) plus a wire-format
extension (`reasoning_tokens` / `reasoning_effort` `Option` fields on
`Request`).

The PR was **closed-not-merged** on 2026-08-12 11:44:41 UTC by the
author after `660c63e` ("merge: resolve all conflicts in favor of main")
left the branch as a non-fast-forwardable merge commit on top of an
already-absorbed snapshot of `main`. The work was then re-derived and
re-landed through 10 separate, smaller PRs that compose the
catalog-driven gating feature in main today.

Closing the orphan `origin/pr/421` ref and posting the linked-PR
comment is the operator-approved path forward (per `the session-4 plan`
§2 D-1, §4.1 B#17, §6.1). The residual `reasoning_gate.rs` is **not**
absorbed by another PR today; that decision is deferred to a future
catalog-extension PR (likely v0.8 scope) when wire-format
backward-compatibility for `reasoning_tokens` is reviewed end-to-end
against every provider.

## 3. Why the closure (not a rebase + re-review)

Three concrete reasons make a rebase-and-merge the wrong move:

1. **No fast-forward target.** The PR tip `660c63e` is a *merge commit*
   over `dec6cdc` (PR head) + `9379a67` (`main` at the moment of
   merge-attempt). Fast-forward would require either (a) a fresh
   rebase of the 253 commits on top of `main@86179b9` — 44 commits
   behind — with every conflict re-resolved, or (b) a squash-merge of
   the whole branch, which loses the per-PR history and re-lands
   5 677 lines already on `main`.
2. **The novel piece (`reasoning_gate.rs`) is the wrong shape today.**
   It was written before the static-catalog PR (#417) shipped; it
   owns its own `ModelsDevEntry` mirror and a `static CATALOG: &[(…)]`
   table that duplicates fields now living in `models_dev.rs`. The
   module needs to be **rewritten** against the live catalog, not
   cherry-picked. A rebase would just transplant dead code.
3. **Wire-format extension is risky in isolation.** The
   `reasoning_tokens` / `reasoning_effort` fields on `Request` add
   two `#[serde(default)] Option<…>` fields that touch every literal
   `Request { … }` construction site in the crate. The absorbing
   PRs (#417, #420, #422, #423, #430) intentionally kept this
   extension **out of scope** to avoid an unrelated wire-format
   review. Picking it up requires its own dedicated PR with a
   provider-by-provider backward-compatibility matrix.

The closure comment below is the operator-approved end-state for
PR #421. The residual `reasoning_gate.rs` is tracked as a follow-up
catalog-extension candidate (likely v0.8 scope, gated on a separate
ticket once `reasoning_tokens` is requested on a real provider
traffic path).

## 6. Post-closure housekeeping (for Phase E)

Once the closure comment is posted and the PR is closed:

1. **No remote ref cleanup.** The PR's ref `refs/pull/421/head` lives
   on GitHub until the PR is closed and aged out by GitHub's ref GC
   (typically a few weeks). No `git push origin :refs/pull/421/head`
   attempt — that ref is server-managed.
2. **Local ref cleanup.** A maintainer can run
   `git fetch origin --prune` to drop the local
   `refs/remotes/origin/pr/421` once the PR is closed on GitHub. This
   is not a destructive operation.
3. **No branch deletion.** This branch was never pushed to a remote
   tip — only `origin/pr/421` (GitHub PR ref) exists. The local
   fetch was ad-hoc for diagnostics; it does not need a `git branch
   -D` because there is no local branch tracking it.
